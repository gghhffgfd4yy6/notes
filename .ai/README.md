# V4 审查/修复流水线（流程规范 v2.0）

> 核心不是"多派几个 Agent"，而是让每一步都有明确的输入、输出和验收条件，并尽可能并行、按依赖分批，压缩等待时间。
> 执行靠人工判断：文档定义流程，不依赖任何自动化脚本。

## 模型总览

```text
并行观察者（分区互不重叠）
   → 候选问题池（按函数分组）
   → 并行裁判（按函数分区批量验证）
   → 修复队列（依赖分析后分批：无重叠并行 / 共享状态串行）
   → 分批独立复核（针对性 + 回归同一轮）
   → 最终仲裁（只处理争议）→ 全量回归 → 发布
```

## 完整流程

```text
当前代码版本
   │
   ▼
① 建立审查任务/快照 + 分区表
   明确 commit、函数/文件清单；每个观察者/裁判一个唯一分区，互不重叠——
   分区约束的是“发现归属”，不限制只读：验证调用链允许跨分区读取
   producer/consumer/helper/cache 等依赖代码；共享调用链作为一个依赖组件
   提供上下文，或交由最终仲裁处理
   │
   ▼
② 并行调查（只读，禁止修改生产代码）
   Agent A / B / C ...
   每份报告末尾必须附"可疑点清单"（函数 / 疑似位置 / 现象，一行一条）
   │
   ▼
③ 报告落盘 + 完整性闸门
   .ai/agent_reports/，每个 Agent 一个独立文件，互不共享
   缺五轴结论 / 缺可疑点清单 / 报告残缺 → 只补跑该分区，不重跑全部
   │
   ▼
④ 候选问题聚类/去重 → 产出 Candidate（不是 Bug），按函数分组
   │
   ▼
⑤ 裁判并行验证（按函数分区，批量验证）
   同函数候选一次源码阅读、批量验证（读一遍，验全部）
   ├─ CONFIRMED ──→ 进入修复队列（下一步做依赖分析）
   ├─ REJECTED（设计行为 / 理论风险 / 已存在修复 / 反证成立——被证明不是 Bug）
   ├─ DUPLICATE / DESIGN / LOW_VALUE
   └─ UNVERIFIED（证据不足 / 未被证明）──→ 不允许进入修复队列；补充证据后复审，或并入最终仲裁
   跨分区重复或争议 ──→ 最终仲裁（只仲裁争议项，不重验全部）
   │
   ▼
⑥ 修复分批（先依赖分析，再动手）
   依赖分析一次：
   ├─ 函数/文件互不重叠 → 独立批次，可并行修
   └─ 共享状态 / 重叠文件 → 串行批次，一次一个
   每项：读取证据 → 读取源码 → 最小修改 → 针对性测试
   每批：git diff 检查（确认未扩大范围）+ 该批回归
   │
   ▼
⑦ 独立复核（并行，按批派发）
   ├─ A 针对性复核：Bug 有没有真的消失
   └─ B 回归复核：有没有破坏其他
   复核未过 → 该项回到修复队列，同批收敛后复验
   │
   ▼
⑧ 全量回归 + Git diff 检查 → 发布版本
```

## 时间压缩原则

1. **发现归属互不重叠**：观察/裁判/复核按函数、文件、行区间唯一划分，杜绝两个 Agent 对同一份代码重复扫或重复认领；只读访问跨分区依赖不受此限（见①）。
2. **并行只给无依赖阶段**：只读调查、批量验证、独立复核可并行；任何"读后再写 / 共享状态"必须串行。
3. **批量代替逐个**：裁判按函数批量验证候选；复核按批派发，不按单个 Bug 来回。
4. **只补跑失败的**：完整性闸门命中时只重跑对应分区/批次，不重跑整个流水线。
5. **回归按批，全量只在发布前**：针对性测试紧跟每项修复；每批一次该批回归；全量回归仅在发布前执行。

## 关键边界

### 去重不是裁判
- 聚类/去重只负责：原始发现 → 标准化 → 候选聚类 → Candidate-NNN
- 输出形如：
  ```
  Candidate-017
  来源: agent-01, agent-04, agent-06
  函数: parsePriceLine
  疑似位置: 120~145
  共同描述: 某类价格与数量关系可能被错误解释
  状态: UNVERIFIED
  ```
- 聚类**不判定**"这是 Bug"

### 裁判由 Codex Agent 做（人工判断，禁止脚本判定）
验证每个 Candidate 必须：
1. 阅读相关源码及调用链（可跨分区只读依赖代码，见①；结论仍归属本分区）
2. 明确构造一个实际触发输入
3. 使用 Node.js 实测
4. 判断实际输出
5. 判断预期输出
6. 检查该行为是否属于项目设计
7. 检查当前版本是否已通过其他代码避免该问题
8. 判断是否影响正常使用

批量验证技巧：同一函数的多个候选，先读一次源码与调用链，再逐个构造触发输入实测，避免重复阅读。

禁止仅依据 Agent 报告下结论；禁止因多个 Agent 同时提出而直接认定为 Bug。
最终只能输出六类：**CONFIRMED / REJECTED / DUPLICATE / DESIGN / LOW_VALUE / UNVERIFIED**

### 修复（先依赖分析，再分批）
```text
依赖分析（一次）：
  ├─ 互不重叠（不同函数/文件，无共享状态）→ 独立批次，可并行修
  └─ 有重叠（同函数 / 同文件 / 共享状态）→ 串行批次，一次一个
每项：
  ├─ 读取 Bug 证据
  ├─ 读取源码
  ├─ 制定最小修改方案
  ├─ 修改
  └─ 针对性测试（立即跑）
每批：
  ├─ 原有测试（该批回归）
  ├─ 检查 git diff（确认没有扩大修改范围）
  └─ 标记 FIXED
```
禁止"发现一堆 Bug 一起改"（丢验收）；也禁止"互不相关的 Bug 排队串行"（浪费时间）。

### 复核分两种（不能混，同一轮并行派发）
- **A. 针对性复核**：Bug 有没有真的消失？
- **B. 回归复核**：修复有没有破坏其他东西？

复核按批派发；复核未过 → 回到修复队列，同批收敛后复验。

## 七条铁律

1. **审查 Agent 不允许修改生产代码。**
2. **不同 Agent 不共享结果文件。**
3. **Deduplication 只产生 Candidate，不产生 Bug 判定。**
4. **Bug 必须经过源码分析 + 实际触发 + 预期行为验证。**
5. **共享状态修改必须串行；互不重叠的修改可以并行。**
6. **每个修复必须有针对性测试，并通过完整回归测试。**
7. **修复完成后必须由独立 Agent 再验证，不能让修复 Agent 自己证明自己没错。**

## 沙箱约定
- 审查/复核阶段：只读权限（workspace-write 足够）
- 修复阶段：才需要完整权限
