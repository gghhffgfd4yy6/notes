# V3 审查/修复流水线（流程规范 v1.0）

> 核心不是"多派几个 Agent"，而是让每一步都有明确的输入、输出和验收条件。
> 执行靠人工判断：文档定义流程，不依赖任何自动化脚本。

## 模型总览

```
多个观察者 → 候选问题池 → 一个裁判层 → 确认的 Bug → 一个执行者 → 测试 → 多个独立观察者 → 最终裁判
```

## 完整流程

```
当前代码版本 v3.xxx
   │
   ▼
① 建立审查任务/快照（明确范围：哪些函数、哪个 commit）
   │
   ▼
② 并行调查（只读，禁止修改生产代码）
   Agent A / B / C / D / E ...
   │
   ▼
③ 原始报告全部落盘（每个 Agent 一个独立文件，互不共享）
   │
   ▼
④ 候选问题聚类/去重 → 产出 Candidate（不是 Bug）
   │
   ▼
⑤ 中央裁判逐个验证
   ├─ CONFIRMED ──→ 进入修复队列
   ├─ REJECTED   （设计行为 / 理论风险 / 证据不足 / 已存在修复）
   ├─ DUPLICATE
   ├─ DESIGN
   ├─ LOW_VALUE
   └─ UNVERIFIED ──→ 不允许进入修复队列
   │
   ▼
⑥ 制定修复方案（最小修改）
   │
   ▼
⑦ 串行修复，一次一个（共享状态修改必须串行）
   │
   ▼
⑧ 每个修复立即测试
   ├─ 通过 → 下一个 Bug
   └─ 失败 → 回滚/重新分析
   │
   ▼
   全量回归测试
   │
   ▼
⑨ 独立 Agent 并行复核（分两类，见下）
   │
   ▼
⑩ 最终裁判 + Git diff 检查 → 发布版本
```

## 关键边界

### 去重不是裁判
- 聚类/去重只负责：原始发现 → 标准化 → 候选聚类 → Candidate-NNN
- 输出形如：
  ```
  Candidate-017
  来源: agent-01, agent-04, agent-06
  函数: parsePriceLine
  疑似位置: 120~145
  共同描述: 某类价格与数量关系可能被错误解释
  状态: UNVERIFIED
  ```
- 聚类**不判定**"这是 Bug"

### 裁判由 Codex Agent 做（人工判断，禁止脚本判定）
验证每个 Candidate 必须：
1. 阅读相关源码及调用链
2. 明确构造一个实际触发输入
3. 使用 Node.js 实测
4. 判断实际输出
5. 判断预期输出
6. 检查该行为是否属于项目设计
7. 检查当前版本是否已通过其他代码避免该问题
8. 判断是否影响正常使用

禁止仅依据 Agent 报告下结论；禁止因多个 Agent 同时提出而直接认定为 Bug。
最终只能输出六类：**CONFIRMED / REJECTED / DUPLICATE / DESIGN / LOW_VALUE / UNVERIFIED**

### 修复（串行，一次一个）
```
BUG-017
  ├─ 读取 Bug 证据
  ├─ 读取源码
  ├─ 制定最小修改方案
  ├─ 修改
  ├─ 针对性测试
  ├─ 原有测试（回归）
  ├─ 检查 git diff（确认没有扩大修改范围）
  └─ 标记 FIXED
然后才处理 BUG-018
```
禁止"发现 17 个 Bug 一起修"。

### 复核分两种（不能混）
- **A. 针对性复核**：Bug 有没有真的消失？
- **B. 回归复核**：修复有没有破坏其他东西？

## 七条铁律

1. **审查 Agent 不允许修改生产代码。**
2. **不同 Agent 不共享结果文件。**
3. **Deduplication 只产生 Candidate，不产生 Bug 判定。**
4. **Bug 必须经过源码分析 + 实际触发 + 预期行为验证。**
5. **共享状态修改必须串行。**
6. **每个修复必须有针对性测试，并通过完整回归测试。**
7. **修复完成后必须由独立 Agent 再验证，不能让修复 Agent 自己证明自己没错。**

## 沙箱约定
- 审查/复核阶段：只读权限（workspace-write 足够）
- 修复阶段：才需要完整权限
