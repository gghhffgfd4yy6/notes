# 五轴审查清单（审查/复核时逐项核对）

> 依据：`.ai/skills/code-review-and-quality/`（五轴审查）
> 用法：审查每个变更/修复时，逐轴核对；任一轴有疑问 → 记录到审查报告，不放过。

## ① 正确性（最重要）

- [ ] 修复是否真正解决目标问题（有复现步骤/用例支撑）？
- [ ] 边界处理：空值 / 0 / 超长 / 特殊字符（emoji、全角、控制字符）？
- [ ] 错误路径：网络失败 / 磁盘满 / 权限拒绝 / 解析失败时的降级？
- [ ] 新测试是否验证了修复本身（而非只验证旧行为）？
- [ ] 故障注入测试是否覆盖（缓存写失败、恢复失败、IO 错误）？

## ② 可读性 & 简洁性

- [ ] 命名是否描述意图（无 temp/data/x 等无意义名）？
- [ ] 是否有重复逻辑可提取？
- [ ] 注释解释"为什么"（而非复述"做什么"）？
- [ ] 函数是否单一职责、长度可控？

## ③ 架构

- [ ] 改动是否符合既有分层（抓取/过滤/判重/推送/存储）？
- [ ] 是否引入循环依赖或跨层调用？
- [ ] 配置外置（密钥/参数不进代码）？
- [ ] 是否破坏模块边界（单文件主程序与测试的依赖关系）？

## ④ 安全

- [ ] 输入是否校验（外部内容不直接进 HTML/日志/推送）？
- [ ] 路径逃逸防护（../ 、符号链接、绝对路径注入）？
- [ ] 日志/错误是否脱敏（密钥、token 不落盘）？
- [ ] 注入面：URL、正则、模板字符串的转义与边界？

## ⑤ 性能

- [ ] 大数据量（万级）是否索引化/有界（不 O(N²)）？
- [ ] 缓存是否上限滚动淘汰（不无限增长）？
- [ ] 同步阻塞点是否可接受（磁盘 IO 频率）？
- [ ] 性能用例（saveBatch 5000 条等）是否达标？

## 提交流程检查（合并前）

- [ ] 全量测试通过（npm test）
- [ ] lint 通过（npm run lint）
- [ ] 版本闸门通过（node .tools/check-version.js）
- [ ] 改动范围与提交信息一致（原子提交）
- [ ] 双远程推送确认（origin + gitee）
